Round 01 · 选手档案

四个工具，四种完全不同的「强」

它们的差异不在于谁更聪明，而在于「交付形态」不同：对话框、长文档、IDE 仓库、办公成品。搞混这一点，就会用错工具。

GPT

ChatGPT

OpenAI · 通用型全能选手

点子最快落地
擅长把「模糊的想法」在十分钟内变成「能看见的东西」，生态和插件最全。

优势

  • 多模态强，文案、分析、图形、代码一站搞定
  • 对话式迭代快，适合脑暴玩法与数值
  • 生态成熟，第三方集成与教程最多

短板

  • 长任务容易丢细节，需要反复贴上下文
  • 不是 IDE，多文件工程要人肉搬运
  • 偶尔「自信地」编造 API 或参数
做游戏时：负责开场脑暴、玩法循环设计、写文案与说明。
CL

Claude

Anthropic · 长文本与代码理解

第一版代码最干净
长上下文里最稳的那一个，擅长把设计文档一次性变成结构清晰、注释合理的代码。

优势

  • 长文档 / 大文件理解稳，几乎不跑偏
  • Artifacts 能直接产出可运行的单页
  • 重构与 Review 语感好，实现偏保守可靠

短板

  • 单文件很强，真实多文件工程仍需自己搭
  • 玩法调参要靠人反复试、再把结果贴回去
  • 能力边界受客户端工具链影响较大
做游戏时：负责游戏主循环、物理与碰撞逻辑的初版实现。
TR

Trae

AI IDE · 直接在仓库里干活

真正能上线
不聊天，直接改文件、跑命令、看终端报错，把一个想法变成可维护的工程。

优势

  • 读写项目文件 + 执行命令，改完立刻验证
  • 多文件协同（HTML / CSS / JS 联动）不用搬运
  • 定位精准，适合长期迭代与维护

短板

  • 依赖本地环境，配置或网络问题要自己排查
  • 非工程产出（PPT、软文）不是主场
  • 目标不清晰时容易「做多」，需要收着点
做游戏时：负责把代码落进真实文件、起服务、修 bug、上线。
WB

WorkBuddy

办公与交付导向的助手

成品最好看
关注「最后交给别人看的那一版」，文档、图表、页面包装和讲解都更成体系。

优势

  • 直接产出可交付物：文档、表格、演示、报告
  • 交互式可视化，解释机制特别直观
  • 擅长串流程：调研 → 产出 → 展示

短板

  • 深层工程问题（性能、构建、调试）覆盖有限
  • 交付风格偏模板化，精细定制需多轮打磨
  • 项目级代码治理不是它的战场
做游戏时：负责页面包装、说明文档、把成果讲清楚。

Round 03 · 做游戏的四个阶段

一个跳跃躲避小游戏，其实分四步

小游戏最容易踩的坑不是「不会写」，而是「写出来不好玩」。下面每一阶段都标了最适合上场的工具。

STEP 01

玩法定义

核心动词只有一个：跳。再决定次要动词（二段跳、下蹲）、失败条件、计分方式和难度曲线——这些是「好不好玩」的地基。

ChatGPTWorkBuddy
STEP 02

主循环实现

requestAnimationFrame 循环、重力与跳跃初速度、AABB 碰撞、障碍生成间距随速度收紧。这一层最需要稳定、可读的代码。

ClaudeTrae
STEP 03

试错与调参

跳跃高度够不够翻过障碍？飞行物该在哪个高度才「必须蹲」？间距太密会劝退、太松会无聊。这步只能真跑起来改数字。

TraeChatGPT
STEP 04

包装与交付

说明文案、键位提示、移动端按钮、视觉风格、最高分记忆——把「能跑」变成「别人愿意点开玩第二局」。

WorkBuddyClaude
Round 04 · 成品试玩

跃迁者 JUMP DODGE

地面尖刺要跳，空中无人机要蹲，金币顺手捡。速度会越来越快，间距不会等你。史上最高分存在你自己的浏览器里。

为什么是这几个数字

跳跃初速 −13.5、重力 0.75，最大跳跃高度约 121px；地面最高障碍 56px，留了 2 倍余量，保证「看起来能过就真能过」。

无人机为什么必须蹲

它悬在离地 42–72px 的区间：站立身高 52px 正好撞上，下蹲后 30px 恰好穿过。机制靠几何而不是靠说明文字。

难度是怎么涨的

速度随距离线性上升，同时把障碍生成间距按速度等比放大，保证反应时间不会随难度崩塌——这是「难但不冤」的关键。
